# GreenLens — Streamlit MVP

기획서 8-2의 5개 화면을 구현한 검토 화면입니다.

```
1 광고 입력 → 2 분석 진행 → 3 검토 Report → 4 보완 및 재검토 → 5 최종 확인
```

## 실행

데이터 파일 `GreenLens_40제품_스키마보완본_v7_1.xlsx`는 이 폴더 또는 **상위 폴더**에
있으면 자동으로 찾습니다. 다른 위치라면 `GREENLENS_DATA` 환경변수로 지정하세요.

```bash
pip install -r requirements.txt
python -m streamlit run app.py
```

API 키 없이 동작합니다. 판정은 규칙 비교 11종, Claim 추출은 규칙 패턴 15종으로 이루어집니다.
LLM 보조(설명문 생성·범위 해석 참고·Policy RAG·증빙 텍스트 구조화)를 쓰려면 실행 전에
`OPENAI_API_KEY`를 설정하고 requirements.txt의 주석 처리된 패키지를 설치하세요.
LLM이 있어도 **판정 상태는 바뀌지 않습니다.**

## 파일 구성

| 파일 | 설명 |
|---|---|
| `app.py` | Streamlit 화면. 판정 로직은 들어 있지 않습니다. |
| `greenlens_core.py` | 검토 파이프라인. **노트북에서 자동 생성되므로 직접 고치지 마세요.** |
| `build_core.py` | `GreenLens_v8_Pipeline.ipynb` → `greenlens_core.py` 생성 스크립트 |
| `requirements.txt` | 의존성 |

노트북을 수정한 뒤에는 반드시 다시 생성해야 화면에 반영됩니다.

```bash
python build_core.py
```

평가 정답표(`test_cases` 시트)를 읽는 코드는 `greenlens_core.py`에 포함되지 않습니다.
정확도 평가는 노트북 9·9.5절에서만 수행합니다.

## 화면별 구현 내용

**1 광고 입력** — 제품 선택(시연 카탈로그 40건 / 전체 358건 / **직접 입력**), 광고 문구 입력, 증빙 첨부(선택).
예시 버튼 4개로 기획서 시나리오를 바로 불러옵니다. 입력을 바꾸면 이전 검토 결과가 초기화됩니다.

**2 분석 진행** — ① Claim 추출 → ②③④ 기준 검색·근거 조회·대조를 Claim 단위로 표시합니다.

**3 검토 Report** — Claim마다 원문 위치를 하이라이트하고, 검토 결과(근거 확인 / 일부 확인 /
불일치 / 자료 요청)와 담당자 확인 상태를 **분리해서** 보여줍니다. 판단 기준·확인한 자료·부족한
자료·처리 경로를 탭으로 나누며, 자료마다 출처 유형(공식·공개 기록 / 기업 제출 / 가상 합성)을 표시합니다.

**4 보완 및 재검토** — 자료 요청 Claim에는 필요한 자료를 구체적으로 요청합니다. 자료 제출은
세 경로를 지원합니다.

- **직접 입력** — 수치·단위·적용 범위·인증번호·유효기간을 항목별로 입력. 이미지 PDF의 수동 입력 경로이기도 합니다.
- **파일 첨부** — 텍스트 추출이 가능한 PDF·TXT. 이미지 PDF는 추출 실패를 알리고 직접 입력으로 안내합니다(OCR은 후속 과제).
- **시연용 샘플** — 준비된 합성 자료. 화면에 가상 자료임을 표시합니다.

문구를 수정하면 **수정문에서 Claim을 다시 추출해** 재검토하고, 변경 전후를 함께 표시합니다.

**5 최종 확인** — Claim별 확인 완료 / 보류를 기록하고, 검토 기록을 JSON으로 내려받습니다.

### 목록에 없는 제품 — 임시 제품과 자가 신고 방지

기획서 페르소나의 제품은 대개 Company DB에 없습니다. '목록에 없는 제품 직접 입력'으로
제품명·회사명·제품군을 넣으면 그 제품으로 검토할 수 있습니다.

- 제품군은 **선택 사항**입니다. 적용할 인증기준을 좁히는 데만 쓰며, '모름'으로 두어도
  검토는 진행됩니다. 다만 기준을 특정하지 못하면 '자료 요청'으로 처리되고 담당자 확인이 필요합니다.
- 제품군 선택지는 기획서가 정한 **대상 업종(생활소비재)** 중 인증기준이 등록된 5종입니다
  (EL302 세탁용 세제 · EL303 주방용 세제 · EL305 다목적 세정제 · EL308 샴푸·린스 및 바디클렌저 · EL309 화장비누).
- 입력한 제품은 **이번 검토에만** 쓰이며 Company DB에 저장되지 않습니다
  (`register_session_product` → 메모리, SQLite 쓰기 없음). 영구 등록은 기획서대로
  운영자가 자료를 검증한 뒤 수행하는 별도 절차로 남겨 뒀습니다.
- 화면에는 `임시 제품 · Company DB 미등록` 배지가 붙고, Report에 `product_origin: SESSION`으로 남습니다.
- 공개 인증 기록이 없으므로 대부분 '자료 요청'으로 시작합니다. 이것이 정상 동작입니다.

**자가 신고로는 인증을 통과할 수 없습니다.** 사용자가 제출한 자료(`origin=SESSION`)만으로
인증 주장을 '근거 확인'으로 처리하면, 자기가 낸 자료로 자기 주장을 승인받는 순환이 됩니다.
인증 '사실'은 공개 인증내역으로 조회할 수 있으므로 인증번호를 역조회합니다.

| 상황 | 결과 |
|---|---|
| 공개 인증내역에 없는 번호 | `자료 요청` · 발급기관 발행 인증서 요청 |
| 공개 인증내역에 있으나 다른 제품 등록분 | `자료 요청` · 등록 제품명을 제시하고 대상 일치 확인 요청 |
| Company DB 등록 자료로 대조 | 기존대로 `근거 확인` |

재생원료 함량 확인서처럼 **공개 조회가 불가능한 문서**는 기획서 시나리오 C대로 세션 제출을
그대로 사용합니다. 기획서가 명시한 대로 "검색된 자료의 존재와 자료 내용의 진실성은 구분"하며,
담당자의 자료 승인이 문서 위조나 제품 실물 품질까지 보증하지는 않습니다.

### 근거를 못 찾았을 때 — 검색 실패 vs 자료 부재

기획서 7절의 ⑤ 분기입니다. 저장소 성질에 따라 대응이 다릅니다.

| 저장소 | 성질 | 실패 원인 | 대응 |
|---|---|---|---|
| Policy KB | 검색 | 질의가 빗나감 | 질의를 재구성해 **1회만** 재조회 |
| Company DB | 정형 조회 | 제품 식별자·모델명 불일치 | 재조회하지 않고 **식별 확인을 사람에게 요청** |

화면에서는 Claim마다 `원인 분기 — [검색 실패 / 자료 부재 / 검수 상태]`로 표시하고,
'처리 경로'에서 그래프가 실제로 지나간 노드를 보여줍니다. 제품 식별이 의심되면 자료를
요구하는 대신 후보 제품을 제시해 고르게 합니다.

## 표시 원칙

기획서 8-2·9절을 화면에서 지키는 부분입니다.

- "친환경 인증 완료", "100% 합법", "그린워싱 아님 확정" 같은 배지를 쓰지 않습니다.
  '근거 확인'도 승인으로 읽히지 않도록 초록색을 쓰지 않습니다.
- 검토 결과와 담당자 확인 상태를 항상 나란히, 그러나 별개로 표시합니다.
- 근거를 찾지 못하면 판정하지 않고 필요한 자료를 요청하며, 자료 부재를 거짓으로 단정하지 않습니다.
- 합성 자료에는 가상 자료 표기를 붙이고, 실제 제품의 측정값을 보증하지 않는다고 명시합니다.
- 사전점검 참고자료라는 고지를 사이드바와 최종 화면에 상시 노출합니다.
- 제출 자료는 세션 범위로만 쓰이며 Company DB에 적재되지 않습니다(AI는 쓰기 권한 없음).

## 대상 업종

기획서 2·6절은 대상 업종을 생활용품·화장품 등 **생활소비재**로 정하고, ACCC 점검에서 우려
주장 비율이 가장 높았던 업종이라는 근거를 붙였습니다. 코드에서는 이렇게 다룹니다.

```python
MVP_PRODUCT_GROUPS  = ("EL302", "EL303", "EL305", "EL308", "EL309")  # 제품군 선택지
NON_CONSUMER_GROUPS = ("EL172", "EL253")                             # 가구 · 이중 바닥재
```

`criteria_master`와 `product_master`에는 가구(8건)·이중 바닥재(4건)가 남아 있지만 화면
선택지에서는 제외합니다. 데이터를 지우지 않는 이유는 확장 시 그대로 쓰기 위해서입니다.

## 알려진 제약

- Claim 추출은 한국어 규칙 패턴 기반입니다. 표현이 크게 다르면 '미지원 유형'으로 분류되어
  담당자 확인으로 넘어갑니다. 조용히 통과시키지는 않지만 자동 검토율은 떨어집니다.
- 자료 보충은 Claim당 1회입니다(`MAX_HUMAN_ROUNDS`).
- 평가셋 TC-010(DEV)은 가구 제품(`P-F003`)을 씁니다. 화면에서는 제외했지만 정답표에는
  남아 있어, 대상 업종을 엄격히 맞추려면 정답표 구성을 바꿔야 합니다(24건 구성 변경).
- 임시 제품은 프로세스 메모리에 남습니다. '새 검토 시작'에서 지우지만, 서버가 계속 떠 있으면
  이전 세션의 임시 제품이 메모리에 남을 수 있습니다(다른 세션에 노출되지는 않습니다).
- 제품 식별 후보는 같은 회사·같은 제품군 안에서 이름 유사도로만 찾습니다. 회사를 잘못 고른 경우나
  모델명 체계가 다른 경우는 찾지 못하며, 이때는 자료 부재로 분류됩니다.
- Policy 재조회는 1회로 제한됩니다(`MAX_POLICY_ATTEMPTS`). 두 번 이상 질의를 바꿔야 하는 경우는 다루지 않습니다.
